PoC 总体说明

背景 · 目标 · 评估框架

1.1 背景

联影正在建设企业级数据平台，统一管理全域数据资产，为 AI Agent、BI 分析等上层应用提供高效、可靠、可治理的数据服务。核心数据来源包括：SAP S/4 HANA、SAP ME、PTC Windchill、CRM（Salesforce）等结构化系统；飞书协作平台（结构化表格 + 非结构化文档）；以及 PDF/Word/Excel/PPT 等制度与技术文档。

1.2 PoC 目标

  • 验证结构化与非结构化数据的统一纳管，重点验证非结构化数据如何供 Agent 用数；
  • 验证从源数据到指标的端到端链路（集成 → 开发 → 治理 → 服务 → 应用）；
  • 验证平台差异化能力——非结构化「存储与索引解耦」架构及混合检索。

场景一：Data for AI — AI 财务分析

权重 40% · 多模态融合问数

2.1 业务背景

财务分析是联影 AI 转型的优先场景，同时涉及结构化财务指标（预算、预实、费用）与非结构化制度文档（预算管理办法、报销制度、超预算审批流程）。本场景验证数据平台能否在同一底座上支撑 Agent 的融合问数。

2.2 场景描述

构建 AI 财务分析助手，支持：

  • 结构化问数：「研发部 Q1 差旅费预算执行率？申请总额多少？」
  • 文档检索：「差旅费超预算审批流程是什么？」
  • 融合问数：「研发部 Q1 差旅费为何超预算？制度如何规定处理方式？」

2.3 数据源与全链路

数据类型数据源（PoC 样例）存放位置接入方式Agent 读取路径
预算申请飞书多维表格（构造）数仓 ODS/DWD 数据集成 · 飞书表格数据源Agent → 结构化问数 → 数仓宽表
预算/费用执行PoC 构造库表数仓 dws_budget_actual / dwd_expense_detail 数据集成 · JDBCAgent → NL2SQL / 语义指标
多源合并宽表申请 + 执行关联dwd_budget_apply_exec_wide 数据集成 · 关联合并算子融合问数结构化侧 evidence
制度/案例文档Word/PDF/Excel（含飞书导出）对象存储 + 数仓 chunk 索引表 文档入库 → 解析 → 一键入库 DorisAgent → 统一检索服务 → 数仓索引

2.4 演示故事线

财务人员在飞书多维表格提交差旅费预算申请；PoC 库表维护对应部门科目的预算执行数据；制度文档经文档入库平台写入数仓索引。用户向 Agent 提问：「研发部 Q1 差旅费申请总额、执行率多少，超预算如何处理？」Agent 返回宽表指标，并引用《预算管理办法》相关条款，输出带 document_id 与数据来源的可追溯 evidence。

类型示例问题数据来源验收点

文档检索差旅费超预算审批流程？统一检索服务 → chunk 索引带 document_id 引用

2.7 关键能力展示点

  • ⭐ 多模态统一纳管：结构化宽表与非结构化 chunk 索引共存于数仓引擎；
  • ⭐ 统一数据服务：Agent 结构化问数走数仓 SQL/语义层，文档检索走统一检索服务；
  • ⭐ RAG 全链路：文档解析 → 切片 → Embedding → 入库 → 混合检索 → 引用溯源；
  • 数据权限：按部门/角色过滤检索与 SQL 结果；
  • 数据血缘：Agent 回答可追溯到原始表字段或文档片段。

2.8 预期 Demo 效果

用户在对话界面提问，Agent 实时拉取结构化指标 + 检索制度文档，输出综合分析。后台可展示：数据请求链路、每步调用的数据资产、evidence 样例（指标行 + 文档 chunk）。

场景二：BI 分析 — 营销域订单 OTD 全链路

权重 25% · 源数据到指标到看板

3.1 业务背景

联影当前 BI 报表建设分散，各部门自行取数、用数，缺乏统一口径和指标管理。本场景验证平台是否具备从源数据管理 → 数据开发 → 数据治理 → 指标构建 → BI 展示的完整链路能力。

本次 PoC 选用子场景 C：销售合同订单全生命周期分析（营销域 OTD 主线），聚焦线索/商机/订单/发运/签收最小闭环。

3.2 测试目标

以营销域订单 OTD 场景串联数据集成、指标语义层、自助分析看板能力；须按 ODS / DWD / 语义层 / BI 最小链路完整演示，验收聚焦可验证的功能输出与响应效果。

3.3 痛点与优化目标

痛点类别现状问题业务影响优化目标
数据割裂线索、商机、订单、发运、签收分散在 CRM/ERP/WMS无法形成营销到交付闭环打通全链路数据
口径不一致OTD、延期、有效订单口径各部门不一跨部门复盘效率低统一指标模型
异常定位慢延期原因散落备注与物流节点问题发现滞后异常归因与预警
过程不可视管理层只看结果缺少过程视图无法提前干预经营总览+过程诊断双层看板

3.7 数据链路要求（全链路覆盖）

  • 数据集成：多源批采集、字段映射、增量同步（PoC 样例）；
  • 数据开发：ODS → DWD → DWS/ADS 建模与调度编排；
  • 数据治理：元数据、质量规则（空值/重复/脱敏样例）、血缘追溯；
  • 指标管理：原子/派生指标定义、指标目录、口径版本；
  • 数据服务：指标 API / 自助取数接口；
  • BI 展示：看板构建、下钻联动、权限分级、导出订阅（PoC 验证核心项）。

3.8 预期 Demo 效果

端到端演示：创建数据集成任务 → 查看元数据 → 开发数据模型 → 定义 OTD 指标 → 生成 BI 看板 → 点击数值查看血缘追溯。完整走通「从元数据到指标」全链路。

3.9 测试与验证过程

  1. 数据库表设计与多源对接：验证数据集成多源接入能力；
  2. ETL 处理与清洗：验证合并、汇总、过滤等能力；
  3. 数据治理：构造空值、重复、脱敏等样例问题；
  4. 语义层构建：验证维度/指标模型与指标集输出；
  5. BI 看板：验证可视化、下钻、筛选、权限与日志审计。

场景三：非结构化数据存储与索引解耦

权重 15% · 平台差异化能力

4.1 场景名称

「对象存储 + 数仓索引解耦」—— 非结构化知识可独立演进的企业 RAG 底座

4.2 业务背景与痛点

  • 制度、案例、技术文档分散在飞书、文件服务器、业务系统附件中，格式多样；
  • 传统方案将「原文存储」与「检索索引」绑死在同一产品，重建索引往往影响上层 Agent 配置；
  • 结构化数仓与向量检索分属不同系统，运维与采购成本高。

4.3 差异化能力说明

核心设计：对象存储（OSS）存原文；Apache Doris 4.x 同时承载结构化数仓 + chunk 级混合索引（BM25 + ANN）；文档解析引擎仅负责 Ingest；统一检索服务封装融合逻辑。重建索引或更换 Embedding 模型时，Agent 与 Tool 配置零改动。

4.4 技术方案要点

设计决策方案价值
存储索引解耦OSS 原文 · Doris 索引 · 检索服务独立索引可重建、存储可扩容互不影响
解析与检索分离解析引擎 Ingest Only，在线检索只走 Doris避免双索引通道
混合检索BM25 全文 + ANN 向量，检索层 RRF 融合关键词 + 语义兼顾
一套 Dorischunk 索引表 + 预实/费用宽表共存RAG + 问数统一底座
一键入库文档入库页 → 入库 Worker → Stream LoadPoC 可快速验证写入链

4.5 验证项

验证项操作预期结果
写入上传 Word/PDF → 一键入库当日可检索，registry + chunks 可查
检索Agent 问制度/案例返回 chunk + document_id + oss_uri
解耦重建 chunk 索引（同 document_id 重导）Agent Tool 配置不变，检索仍可用
混合同时问预实数据 + 制度依据双源 evidence 合并回答

4.6 预期 Demo 效果

演示员上传《标杆案例》类文档 → 实时解析切片入库 → 在 Agent 中提问文档相关内容 → 展示引用片段与 OSS 原文链接；随后演示「重建索引后 Agent 无需改配置仍可检索」，对比传统一体化方案的锁定风险。
